# Internationalization (i18n)

AEVOTRON uses `i18next` and `react-i18next` with three supported locales:

- `en` — English
- `ru` — Russian
- `zh` — Simplified Chinese

## Runtime architecture

- `src/lib/i18n.functions.js` resolves the initial locale on the server.
- Locale precedence is the `aevotron-language` cookie, then the weighted `Accept-Language` header, then English.
- `src/lib/locale.js` contains pure parsing and negotiation helpers.
- The root route loader returns the request locale before rendering.
- `LanguageProvider` creates an isolated i18next instance for that render. Do not export or use a process-wide mutable i18next singleton in server-rendered code.
- The selected locale is persisted in a one-year, path-wide, SameSite=Lax cookie. Existing `localStorage` preferences are migrated to the cookie on the first client render.
- The root document receives a matching `lang` attribute. Route titles and descriptions are rendered for the initial request and synchronized after client-side locale changes.
- No MutationObserver or DOM-wide text replacement is used.

## Catalog layout

`src/locales/{en,ru,zh}.json` is the compatibility catalog and fallback namespace (`translation`). New and migrated feature strings belong in domain namespaces:

- `src/locales/auth/{en,ru,zh}.json`
- `src/locales/landing/{en,ru,zh}.json`
- `src/locales/dashboard/{en,ru,zh}.json`

Use the feature namespace first and the compatibility catalog second:

```jsx
const { t } = useTranslation(["auth", "translation"]);
```

The landing page can use the `useLanguage` convenience hook:

```jsx
const { language, t, setLanguage } = useLanguage(["landing", "translation"]);
```

The compatibility namespace remains available while existing screens are migrated. New feature work should use stable semantic keys (for example, `model.description.gpt4o`) rather than visible sentences as identifiers.

## Adding a locale

1. Add the locale code to `supportedLanguages` and locale negotiation in `src/lib/locale.js`.
2. Add a root compatibility catalog at `src/locales/{locale}.json`.
3. Add matching files for every registered domain namespace.
4. Keep interpolation variable names identical across all translations.
5. Use i18next plural suffixes appropriate to the locale (`_one`, `_few`, `_many`, `_other` where applicable).
6. Add the locale to the catalog parity tests before enabling it in the UI.

## Formatting

Use the helpers in `src/lib/formatters.js` for locale-sensitive numbers, currencies, dates, and relative times. Do not use implicit browser-locale formatting such as `toLocaleString()` in application UI.

## Validation

Run:

```sh
npm test
npm run lint
npm run build
npm run build:cloudflare
```

The tests check catalog parity, missing/empty translations, interpolation parity, plural forms, punctuation, namespace parity, locale negotiation, independent i18next instances, and locale-aware formatting.
